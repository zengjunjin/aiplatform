# ADR-004: 选择 SSE 而非 WebSocket 做流式生成

## 状态

已采纳

## 日期

2026-07-04

## 上下文

RAG 问答系统的核心体验之一是将 LLM 生成的答案以流式方式逐 token 返回给前端，避免用户长时间等待。需要在 SSE（Server-Sent Events）和 WebSocket 两种技术方案中选择。

关键约束：
- 数据流向为单向：服务端 → 客户端（LLM token 流）
- 需要与现有 HTTP 基础设施兼容（Nginx 反向代理、认证中间件）
- 需要支持断线重连
- 实现复杂度应尽可能低

## 决策

选择 **SSE（Server-Sent Events）** 作为流式生成协议。

核心理由：
1. **单向数据流匹配**：LLM 生成场景是典型的服务端推送，客户端只需接收，天然适合 SSE
2. **HTTP 兼容**：SSE 基于标准 HTTP 协议，无需升级协议，与现有 Nginx 反向代理、JWT 认证中间件完美兼容
3. **实现简单**：FastAPI 原生支持 `StreamingResponse`，客户端使用 `EventSource` API 即可，无需额外库
4. **自动重连**：浏览器原生 `EventSource` 内置自动重连机制

## 后果

### 正面影响

- 实现简单，服务端和客户端代码量极少
- 与现有 HTTP 基础设施（Nginx、JWT 认证、CORS）完全兼容
- 浏览器原生 `EventSource` 支持自动重连
- 调试方便，可用 curl 直接测试

### 负面影响

- 只支持单向通信（服务端→客户端），如需双向需另配 WebSocket
- 浏览器限制每个域名最多 6 个并发 SSE 连接
- 不支持二进制数据（但 LLM token 流为文本，非问题）
- IE 浏览器不支持（项目中不考虑 IE 兼容性）

## 替代方案

| 方案 | 优点 | 缺点 | 为何未选择 |
|------|------|------|------------|
| WebSocket | 全双工通信、低延迟、支持二进制 | 需协议升级、Nginx 需额外配置、认证方式不同、实现复杂 | 双向通信在当前场景是过度设计 |
| 轮询 (Polling) | 实现最简单、兼容性最好 | 延迟高、资源浪费、用户体验差 | 延迟不可接受，不符合流式体验要求 |
| gRPC Stream | 高性能、强类型、双向流 | 浏览器端支持有限（需 grpc-web 代理），框架复杂度高 | 浏览器兼容性差，增加架构复杂度 |
