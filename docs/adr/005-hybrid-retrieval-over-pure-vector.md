# ADR-005: 选择混合检索（BM25 + 向量 + RRF）而非纯向量检索

## 状态

已采纳

## 日期

2026-07-04

## 上下文

RAG 系统的检索质量直接影响最终回答的准确性。需要在检索策略上做出选择：使用纯向量（语义）检索，还是结合关键词检索的混合方案。

关键约束：
- 知识库文档可能包含专有名词、代码片段、编号等精确匹配需求
- 向量检索擅长语义匹配，但对精确关键词匹配（如"API v2.0"、"error code 500"）效果不佳
- 需要一种融合策略，在不引入复杂调参的前提下结合两种检索结果

## 决策

选择 **混合检索方案**：BM25 关键词检索 + 向量语义检索，通过 **RRF（Reciprocal Rank Fusion）** 融合结果。

核心理由：
1. **关键词匹配 + 语义匹配互补**：BM25 擅长精确关键词匹配（专有名词、代码、编号），向量检索擅长语义相似度匹配，两者结合覆盖更全面
2. **RRF 无需调参**：与传统加权融合（需调权重超参）不同，RRF 仅基于排名融合，无需额外参数，鲁棒性强
3. **业界验证**：混合检索 + RRF 是 RAG 领域广泛验证的有效方案，Weaviate、Cohere 等均有实践

## 后果

### 正面影响

- 检索召回率显著提升，精确匹配和语义匹配场景均有覆盖
- RRF 融合无需调参，降低维护成本
- BM25 实现简单，基于 scikit-learn 的 `TfidfVectorizer`，无额外依赖
- 可针对不同知识库类型灵活调整（如代码库可提高 BM25 权重）

### 负面影响

- 检索阶段需两次查询（向量 + BM25），增加约 10-20ms 延迟
- 需维护 BM25 索引，文档更新时需同步刷新
- 文档量极大时（>100 万 chunk），BM25 索引内存占用增加

## 替代方案

| 方案 | 优点 | 缺点 | 为何未选择 |
|------|------|------|------------|
| 纯向量检索 | 实现简单、单次查询、语义理解好 | 精确关键词匹配弱，专有名词/代码片段检索效果差 | 无法满足精确匹配需求 |
| 纯 BM25 | 精确匹配强、速度快、可解释性好 | 无语义理解能力，同义词/改写无法匹配 | 无法满足语义匹配需求 |
| 加权融合 | 灵活可控，可针对场景调优 | 需要调参，不同知识库需不同权重，维护成本高 | 调参复杂，泛化性差 |
| 学习排序融合 | 理论上最优，端到端优化 | 需标注数据、模型训练、推理延迟高 | 项目初期无标注数据，过度工程化 |
