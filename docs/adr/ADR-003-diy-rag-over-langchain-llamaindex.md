# ADR-003: 自建 RAG 管线而非使用 LangChain/LlamaIndex

## 状态

已采纳

## 日期

2026-07-04

## 上下文

在构建 RAG（检索增强生成）问答系统时，市面上有成熟的框架如 LangChain 和 LlamaIndex，它们提供了开箱即用的 RAG 管线、文档加载器、检索器、Chain/Agent 等抽象。

项目面临选择：使用成熟框架快速搭建，还是从零自建 RAG 管线。

关键约束：
- 项目是个人学习/展示项目，需要深入理解 RAG 原理
- 需要完全控制检索和生成流程，便于定制优化
- 避免框架版本升级带来的 breaking changes
- 面试展示价值：自建管线体现对 RAG 原理的深入理解

## 决策

选择 **自建 RAG 管线**，不依赖 LangChain 或 LlamaIndex。

核心理由：
1. **避免框架锁定**：LangChain/LlamaIndex 版本迭代快，API 频繁变动，迁移成本高
2. **深入理解原理**：自建管线迫使团队理解检索、融合、重排序、提示工程等每个环节，这在面试中极具展示价值
3. **完全可控**：检索策略（BM25、向量、RRF 融合）、重排序、prompt 构造均可自由定制
4. **减少依赖**：框架引入大量传递依赖，增加安全审计和维护负担

## 后果

### 正面影响

- 对 RAG 每个环节有深入理解，便于面试展示和知识沉淀
- 检索、融合、重排序策略完全可控，可针对业务场景优化
- 无框架升级风险，代码稳定性高
- 依赖精简，安全审计范围小
- 代码量可控（核心 rag/ 模块约 500 行），维护成本低

### 负面影响

- 开发初期投入更高（但核心 RAG 管线并不复杂）
- 缺少 LangChain 的 Agent、Tool、Memory 等高级特性（当前项目不需要）
- 缺少社区最佳实践参考，需自行设计架构

## 替代方案

| 方案 | 优点 | 缺点 | 为何未选择 |
|------|------|------|------------|
| LangChain | 生态丰富、文档加载器多、社区活跃 | 抽象层过多、API 频繁 breaking changes、调试困难、过度封装 | 框架锁定风险高，学习成本 vs 收益不成比例 |
| LlamaIndex | RAG 专用、数据连接器丰富、索引结构多样 | 同样存在 API 不稳定问题，定制化受限于框架设计 | 框架约束较多，不利于深入理解 |
| Haystack | 模块化设计、Pipeline 概念清晰、企业支持 | 社区较小，中文生态薄弱 | 社区支持不足，中文场景适配有限 |
