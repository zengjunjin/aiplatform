# ADR-001: 选择 FastAPI 而非 Django/Flask 作为后端框架

## 状态

已采纳

## 日期

2026-07-04

## 上下文

项目启动时需要选择 Python 后端 Web 框架。主流的 Python Web 框架包括 Django、Flask、FastAPI。项目核心需求是构建一个 RAG（检索增强生成）问答平台，涉及大量 LLM API 调用、流式响应、文档处理等 I/O 密集型操作。

关键约束：
- 需要高性能异步处理能力（LLM 调用、向量检索均为 I/O 密集型）
- 需要自动生成 API 文档（OpenAPI/Swagger），方便前后端协作
- 团队希望保持轻量级，避免过重的框架约束
- 需要 WebSocket 和 SSE 支持

## 决策

选择 **FastAPI** 作为后端框架。

核心理由：
1. **原生异步支持**：基于 Starlette + asyncio，天然适合 LLM API 调用、数据库查询、向量检索等 I/O 密集型场景
2. **自动文档生成**：基于 Pydantic 类型注解自动生成 OpenAPI/Swagger 文档，无需额外维护
3. **高性能**：在独立基准测试中性能与 Node.js/Go 接近，远优于传统同步框架
4. **类型安全**：Pydantic v2 提供运行时数据验证和编辑器自动补全支持

## 后果

### 正面影响

- 异步 I/O 大幅提升 LLM 调用和向量检索的并发吞吐
- OpenAPI 文档自动生成，前后端协作效率高
- 类型注解驱动开发，减少运行时错误
- 轻量级，按需引入依赖（对比 Django 的全家桶）

### 负面影响

- 缺少 Django 的 ORM、Admin 后台等内置功能，需自行集成（SQLAlchemy + Alembic）
- 社区生态小于 Django，第三方插件较少
- 异步编程模型对团队有一定学习曲线

## 替代方案

| 方案 | 优点 | 缺点 | 为何未选择 |
|------|------|------|------------|
| Django + DRF | ORM 强大、Admin 后台、社区成熟 | 原生异步支持弱（3.x 才逐步支持），过于重量级，不适合微服务风格 | 异步支持不足，框架过重 |
| Flask | 轻量灵活、社区庞大、学习成本低 | 无原生异步支持，需手动集成 OpenAPI，无类型验证 | 缺少异步能力，需大量手动集成 |
| Sanic | 异步支持、高性能 | 社区较小，生态有限，文档和工具链不完善 | 社区支持不足，维护风险高 |
